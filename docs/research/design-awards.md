### Inferences
- Pick-able signature ideas: (a) variable-font weight/width as live state (Exat), (b) one small procedural world rendered in Three.js (Messenger), (c) single neon accent on a quiet dark ground with blob feedback (Lando Norris). A narrow-scope fit for a learning app is (a)+(b): typography as the hero on the review screen, 3D as a one-scene reward/progress space.
- Motion personality evidenced by these sites: scroll-linked, reversible, velocity-aware (Lenis + GSAP). For a daily-review phone app, keep the same "state not sequence" principle but drive it from drag position rather than page scroll.
- The award sites are scroll-driven marketing pages; none is a task-flow app, so their patterns apply to onboarding/home/progress surfaces, not to the review loop itself.

## 2. Native iOS patterns that translate to the web, and notable web apps implementing them

### Takeaway
Liquid Glass is a material system with explicit "don't" rules (no glass on content, no glass-on-glass, tint sparingly) that a PWA should copy only for the chrome (tab bar, floating controls), not the cards. Web glass refraction is feasible via SVG displacement filters but is Chromium-reliable only, so on iPhone Safari it needs a WebGL/canvas fallback or a plain blur.

### Cited Findings
- Liquid Glass was introduced at WWDC 2025 for iOS 26; two variants: Regular (controls glass for compact elements, standard glass for larger, thicker elements) and Clear/utility; advice: "If glass makes text harder to read, remove the glass"; it responds to Reduce Transparency and Increase Contrast. — [Firefox Acorn: iOS 26 and Liquid Glass](https://acorn.firefox.com/latest/mobile/patterns/i-os-26-and-liquid-glass-w2oH48nk)
- A search summary states Apple updated its Materials guidance in the HIG on September 9, 2025 (semantic use, legibility, contrast, avoid unnecessary glass layers). Secondary only; developer.apple.com content did not load. — search result for [HIG Liquid Glass](https://acorn.firefox.com/latest/mobile/patterns/i-os-26-and-liquid-glass-w2oH48nk) (indirect); [Apple HIG Materials](https://developer.apple.com/design/human-interface-guidelines/materials) (page loaded without body)
- WWDC25 "Meet Liquid Glass" (session 219) transcript points: lensing (bends and concentrates light) is the defining property; objects materialize by modulating lensing rather than fading opacity; elements flex and "energize" on touch, lift during interaction and rest quietly; controls morph between states in one floating plane; shadows get more prominent as text scrolls beneath; larger elements simulate thicker material; nearby colourful content spills light onto glass. Do not: apply glass to the content layer, stack glass on glass, mix Regular and Clear in one app, tint everything (tint only primary actions). — [Apple WWDC25 session 219](https://developer.apple.com/videos/play/wwdc2025/219)
- Web implementation: Aave's "Building Glass for the Web" uses SVG `feDisplacementMap` with a generated red/green-channel displacement map to refract live DOM (text stays selectable, links clickable); quadrant symmetry cuts per-pixel work by 75%; moving glass without reshaping reuses the same map for stable frame rates on mobile; Safari needs workarounds (fresh filter IDs to bust caching, size ceilings on filtered content, no SVG filters on live `<video>`), and a WebGL shader path drives the same displacement map when live DOM cannot be filtered. No publication date given. — [Aave](https://aave.com/design/building-glass-for-the-web)
- General limits (search summary of several tutorials): `backdrop-filter: url(#svg)` refraction works reliably only in Chromium; `backdrop-filter` only affects pixels inside the element bounds (Apple's glass refracts beyond its edges); SVG displacement is not super-sampled (pixelation). Candidate libraries named in results: liquid-glass-js and @real-human/liquid-glass (npm). Sources not individually verified. — [Ekino (Medium; 403 on fetch)](https://medium.com/ekino-france/liquid-glass-in-css-and-svg-839985fcb88d); [DEV: 6 ways](https://dev.to/devyatov/liquid-glass-on-the-web-6-ways-to-build-it-with-css-and-svg-3m07); [WebKit bug 313914](https://bugs.webkit.org/show_bug.cgi?id=313914)
- Gesture grading precedent: Juken (WaniKani client) has no typing; you recall, press-and-hold Reveal (hold prevents accidental activation), then swipe right = correct, left = incorrect; desktop keeps it: space to reveal, arrow keys for swipe; inspired by Anki plus Tinder-style swipes. — [Juken README](https://github.com/oguzgelal/juken/blob/master/README.md)
- Duolingo: in-lesson characters run on an internal system ("Maker") with Rive rigs, real-time lip-sync across 40+ languages; haptics designers compose haptics as an instrument melded into the sound design ("seen, heard, felt"). Date not shown in the results. — [Rive blog](https://rive.app/blog/duolingo-s-ai-powered-video-call-brings-lily-to-life); [Duolingo blog](https://blog.duolingo.com/world-character-visemes)

### Inferences
- Use glass only for the bottom tab bar, a floating "grade" control cluster, and detent sheets (answer details); keep the kanji card itself opaque with high contrast. This obeys Apple's own rule and avoids Safari refraction limits.
- Safari on iPhone is the primary target, and refraction via backdrop-filter+SVG is unreliable there; the safe path is (1) layered blur + inner highlight + specular edge in CSS as the default, (2) optional WebGL-rendered lensing in the one 3D canvas if budget allows. Verify on a real device.
- Sheets with detents, interactive springs and haptics: I found no verified web app that implements detent sheets or Taptic haptics with award-level polish. iOS Safari does not expose the Vibration API (my knowledge; not verified in this session), so haptic "moments" would have to be approximated with motion and sound. Mark as an assumption to test.
- Swipe-to-grade should be paired with always-visible buttons, because swipe-only (Juken) trades speed for accidental grades; Juken's press-and-hold reveal is the evidenced mitigation.

### Gaps
- Apple HIG pages (sheets, materials, haptics) returned no body text; detent behaviour, grabber rules, and Dynamic Island guidance are not verified from primary sources.
- No verified named web apps with sheet detents, interactive spring sheets or haptics; no source for Safari Vibration API support in this session.
- Date/authorship of the Aave and Ekino glass articles unknown (WebKit bug 313914 hints at a 2026-era report but not confirmed).

## 3. What the best flashcard/SRS apps do for mobile review UX, and their weaknesses

### Takeaway
The category's evidenced pain points are small text/cards, top-placed buttons (no one-handed reach), no font-size control, and a functional-not-polished feel; speed-first gesture clients (Juken, Tsurukame) are what power users move to. Duolingo is the benchmark for character, sound and haptic feedback but I found no source on its weaknesses for kanji.

### Cited Findings
- Anki/AnkiMobile: complaints centre on an outdated, unintuitive UI; on iOS users reported being unable to change font sizes despite paying about $25 and limited colour options; strengths are flexibility and the algorithm. — [Nibble: Anki review](https://nibble-app.com/blog/anki-review); [Kimola AnkiMobile feedback report](https://kimola.com/reports/ankimobile-flashcards-insights-and-user-feedback-report-app-store-us-147212) (App Store review aggregation; not individually read)
- April 21-24, 2026: a product designer posted AnkiMobile redesign mockups aligned to Apple HIG on the Anki forum; replies noted AnkiMobile is closed source and changes start on desktop; one user said the current UI is "basically perfect". — [Anki forums](https://forums.ankiweb.net/t/what-about-a-new-user-experience-for-anki/69483)
- WaniKani: no official app; third-party clients Tsurukame (iPhone), Flaming Durtles (Android), Juken (swipe, no typing). — [WaniKani community: Juken](https://community.wanikani.com/t/ios-android-web-juken-review-app-for-wanikani/43841?page=2); [WaniKani for iOS thread](https://community.wanikani.com/t/wanikani-for-ios/1862)
- Bunpro (community reports, undated, various years): font size can't be adjusted in the mobile app (hard to read kanji/furigana); buttons at the top of the screen block one-handed use; requests for larger review cards; remove-from-review button misbehaves; queue ordering bug several reviews into a session; Cloze hints criticized; Japanese font size on desktop shrank, making furigana hard to read. — [Bunpro community feedback](https://community.bunpro.jp/t/feedback-suggested-improvements-feature-request/131/4032); [bug reports](https://community.bunpro.jp/t/feedback-bug-reports/130?page=151)
- jpdb.io: combines a media-based vocabulary database with an SRS to pre-teach words from anime/novels; free with Patreon tiers (from $5/month); UI described as very bare; review-order options locked behind Patreon "labs"; progress bars on media decks feel RPG-like. — [Tofugu: jpdb](https://www.tofugu.com/japanese-learning-resources-database/jpdb-io/); [Reddit thread via mirror, Mar 2024 (pre-window)](https://reddit.rtrace.io/r/LearnJapanese/comments/1biyipl/switching_from_anki_to_jpdbio_has_drastically/kvotfix/?context=3)
- Duolingo: see section 2 (Rive character system, composed haptics).

### Inferences
- Design wins not served by incumbents: big thumb-zone controls at the bottom, a user-adjustable Japanese type size (with furigana scaling), swipe plus button grading, and a visible progress "world" (jpdb's RPG feel plus Duolingo-level feedback).
- The desktop experience can be keyboard-first (Juken's space/arrow mapping) and legitimately different from the phone.

### Gaps
- No usable sources for Renshuu, Kanji Study, or current WaniKani web review UX; Duolingo weaknesses for Japanese not found; App Store ratings/dates not collected.
- Bunpro community posts are undated in my extraction; some may predate October 2024.

## 4. Typography for mixed Latin + Japanese UI (named fonts and licences)

### Takeaway
The only licence facts I could source are that Noto Sans JP, Zen Kaku Gothic New (and Antique), Zen Maru Gothic and Shippori Mincho are SIL OFL 1.1 and on Google Fonts, so they are safe to self-host in a PWA. I could not verify which Japanese fonts the award winners above actually use.

### Cited Findings
- Noto Sans JP, Noto Serif JP, Zen Maru Gothic, Zen Kaku Gothic Antique and others are licensed under SIL OFL 1.1; Zen Kaku Gothic New and Shippori Mincho are also listed under OFL 1.1 and available on Google Fonts. OFL permits use, modification and redistribution (including bundling) as long as the font is not sold on its own and Reserved Font Names are not reused by derivatives. — [search result summary of fontsource/Noto repos](https://github.com/notofonts/noto-cjk/blob/main/Sans/README-third_party.md); [Booth font list](https://booth.pm/ja/items/7474858)
- Exat (Latin) is a commercial typeface from Hot Type, 21 styles / 1,715 glyphs, with Condensed/Normal/Wide widths across seven weights; no evidence it covers Japanese. — [Abduzeedo](https://abduzeedo.com/exat-variable-font-microsite); [Media Marketing](https://www.media-marketing.com/en/news/studio-size-wins-red-dot-best-of-the-best-for-the-presentation-of-the-exat-typeface/)
- Bunpro users report shrunken Japanese font size and furigana legibility issues, supporting size control as a requirement. — [Bunpro community](https://community.bunpro.jp/t/feedback-suggested-improvements-feature-request/131/4032)

### Inferences
- A candidate stack, not evidenced as used by any award winner: a geometric/grotesk Latin display face paired with Zen Kaku Gothic New (UI/body) and Shippori Mincho or Noto Serif JP (kanji hero/stroke-order display); all OFL, so legal to subset and self-host. Subsetting a CJK font to the JLPT set (about 2,300 kanji for N5-N1 plus kana) is needed to keep PWA payload small (engineering inference, not sourced).
- Variable CJK weight (as in the Exat idea) requires a variable Japanese font; Noto Sans JP and Noto Serif JP ship as variable on Google Fonts (my recollection; not verified here), so confirm axes before committing to weight-as-state.

### Gaps
- Fonts actually used by Awwwards/CSSDA/FWA winners, Japanese commercial foundry licences (Morisawa, Fontworks, Fonts.google alternatives for self-hosting), and variable-axis availability were not verified.
- No named Japanese-site typographic case study from the window beyond Nippori Seminar (details unseen).
